# ライブラリを読み込める REPL の方式（repl）

`docs/issues/repl.md`（`docs/wants.md` 20）の段階 1 をどう作るかを決める。issue の完了条件は「対話の入口があること」と「前の入力の効果が再実行されないこと」の両方を要求する。この 2 つを同時に満たす方式が未確認なので、ここで選択肢と費用を並べる。

## 何が難しいか

hado の実行は AOT である。`crates/hado/src/main.rs` の `run_program` は入力ファイルをビルドしてから実行するだけで、評価の状態を次の実行へ持ち越す仕組みが無い。`docs/plan.md` は JIT を v0.2 へ保留している（291 行目「JIT。Cranelift の `JITModule` は `ObjectModule` と同じ `Module` trait なので `emit` を共有できる」、963 行目）。

素直に「入力ごとに、ここまでの入力を全部含むプログラムをビルドして実行する」と、前の入力の効果が毎回やり直される。`Io.log "a" as _ ->` の次に `1 + 1` を打つと `a` が 2 回出る。issue の完了条件はこれを見逃さない。

## 案

### A. JIT を入れる

`docs/plan.md` が保留にしている JIT を今の版へ動かす。`emit` を `ObjectModule` と `JITModule` で共有し、セッションのプロセスを 1 つ保ったまま、入力ごとに新しい関数を足して呼ぶ。束縛した値はそのプロセスのメモリに載ったままなので、効果は 1 回しか走らない。対話も保てる。

- 費用: いちばん大きい。`emit.rs` の分離、JIT 側のシンボル解決（C ランタイムと prelude）、`main` の本体を「継続」として関数化する仕組みが要る。数ラウンド規模。
- 版: `docs/plan.md` の版計画を書き換えることになる。人が決める。

### B. 入力全体を読み切ってから 1 回だけ実行する

標準入力を EOF まで読み、1 つのプログラムとしてビルドして 1 回だけ実行する。効果は 1 回しか走らず、`e as x ->` の束縛も続く。issue の完了条件の文面は満たす。

- 費用: 小さい。入力の完結判定（括弧と閉じる印の釣り合い、行末が `=>`・`|>`・`|`・`,` でないこと）と、`hado repl <dir>` の受け付けだけ。
- 欠点: **対話にならない。** EOF まで何も出ないので、issue の現象「対話的に式を評価する入口が無い」は残る。REPL と呼ばない方がよい。

### C. 効果の結果を記録して、再実行のときに返す（replay）

入力ごとにここまでの入力をビルドし直すが、既に走った効果の結果を記録しておき、2 回目以降は記録した結果を返す。プロセスは入力ごとに起動し直すが、観測される効果は 1 回だけになる。対話は保てる。

- 仕組み: セッションの前口上に、prelude の効果（`Io`）を捕まえる handler を置く。効果の呼び出しごとに通し番号を振り、`(入力の番号, 通し番号)` を鍵にして結果をファイルへ書く。再実行のときは、鍵があればその値を返し、無ければ本来の効果を呼んで書く。
- 費用: 中。前口上の handler を hado で書き、`hado` 側に入力の足し込みと記録ファイルの受け渡しを足す。効果の結果が `Bytes`・`String`・`String List`・`Void` に限られる（prelude の `Io` はそうなっている）ので、記録できる。
- 欠点: 効果の結果が外の状態に依存する場合（`read_file` の後にファイルが変わるなど）は、記録した値を返すので実際と食い違う。REPL の意味としてそこをどう定めるかは仕様の判断になる。利用者が `<dir>` で足した効果は、その効果の操作ごとに同じ仕組みが要る。

### D. mono IR の解釈器を書く

`crates/hado/src/mono.rs` の `Expression` を評価する解釈器を足す。`run` と `repl` が同じ意味になるよう、`once`・`again` と値引数を含む handler の意味を写す必要がある。

- 費用: 大きい。しかも意味が 2 か所（codegen と解釈器）になるので、ずれれば §10・§11・§38 の判定が食い違う。
- 版: 仕様の意味を 2 つ持つことになるので、避けたい。

## 推奨

**A（JIT）**。対話と「効果を 1 回だけ」を同時に満たす唯一の筋で、`docs/plan.md` 自身が「`emit` を共有できる」と見積もっている。ただし版計画を動かすので、人が決めてから着手する。

次点は **C**。JIT を今の版に入れない場合の現実的な落とし所で、対話を保てる。効果の記録の意味（外の状態が変わったときに古い値を返してよいか）を仕様として決める必要がある。

**B は勧めない。** 完了条件の文面は満たすが、issue の現象が残るので REPL ではない。

## 決めること

- JIT を今の版へ動かすか（`docs/plan.md` の版計画の変更）。
- 動かさない場合、C の replay の意味を仕様として認めるか。認めない場合、段階 1 は対話を諦めた B になる。
