# 束縛の名前を式の後ろに書く（postfix-binding）
優先度: 中。

## 現象

束縛（`let p =`）と、値を使わない一歩（`do`）は、行頭のキーワードで始まる。書く側は、計算を書く前に、結果に付ける名前か、値を捨てることを決めることになる。受理コーパスと stdlib で行頭が `let` の行は 20 行、`do` の行は 7 行ある（2026-09-26）。

```
$ grep -rhE '^\s*let\b' tests/accept stdlib --include=*.hd | wc -l
20
$ grep -rhE '^\s*do\b' tests/accept stdlib --include=*.hd | wc -l
7
```

行頭のキーワードは、`if` の後ろに続く `->` がどこに付くかも決めている。`if` は閉じる印を持たず、最後の腕は右端まで伸びる。`do` を `if` の前に置けば `->` は `if` 全体に付き、腕の中に置けば `->` はその腕に付く。

```
$ cat target/issue/whole/main.hd
// needs: prelude
def main =
  let ok = true ->
  do if ok => log "a" | log "b" ->
  log "finish"
$ cargo run --offline -q -- run target/issue/whole/main.hd
a
finish
$ cat target/issue/inarm/main.hd
// needs: prelude
def main =
  let ok = true ->
  if ok => log "a" | do log "b" ->
  log "finish"
$ cargo run --offline -q -- run target/issue/inarm/main.hd
a
```

キーワードを持たない `|>` は、最後の腕の後ろに置くと腕に付く。`Int.to_string` は `2` にだけ掛かり、腕の型が食い違う。

```
$ cat target/issue/pipe/main.hd
def main =
  if true => 1 | 2 |> Int.to_string
$ cargo run --offline -q -- check target/issue/pipe/main.hd
main.hd:2:20: error[E305]: expected Int, found String; expected here at main.hd:2:14
```

## 原因

`crates/hado/src/parser.rs` の `parse_expr` が、先頭の 1 トークンで `parse_let`・`parse_do`・`parse_with`・`parse_branch` に分ける。束縛と一歩の範囲は、このキーワードが開き括弧の役目をして決まる。キーワードを外して `x = e ->` と `e -> body` と書く案は `docs/plan.md` の `Q6` で退けている。退けた理由は、文法規則が 6 本以上増えることと、行頭の 1 トークンでの判別を失うことである。

## 案

- 推奨: 束縛を `e as p ->` と書く（Option は `e as p? ->`）。値を使わない一歩は、キーワード無しの `e ->` と書く。`let` と `do` は廃止し、`with H ->` は前置のまま残す（計算の結果ではなく、この先を handler の下で動かす宣言なので）。
  - `as` は既にキーワードで、使うのは `implement X as Y` と `handler X as Y` の見出しだけである。式を読み終えた直後の 1 トークン（`as` か `->`）で形が決まるので、`|>` と同じ種類の判別で済む。
  - 行頭の判別は `as` を入れた時点で失われる。そのため、`do` を外す追加の費用は `Q6` の見積もりより小さい。`let` の右辺と `->` の境界の問題は、`let` ごと消える。
  - 「実行に意味がある」という `do` の意図は、純粋な式の破棄を拒む E303 がそのまま担う。
  - 名前が左端に縦に並ばなくなるので、どこで何を定義したかを拾い読みしにくくなる。
  - `as` は名付けに限る。型変換は関数で書き（§2）、パターンの中の別名（`Some(x) as whole`）にも使わない。別名が要るときは 2 回束縛する（`e as whole -> whole as Some(x)? ->`）。
  - `?` は名前の側に置く（`e as p? ->`）。`do-option-absent` の推奨を採れば `?` ごと消える。
  - `as` は最も弱く結合し、直前の区切り（`->`・腕の `=>`・本体の `=` と `=>`）から `as` までの式全体を束縛する。`xs |> List.map f as ys ->` はパイプライン全体を、`1 + 2 as x ->` は和を束縛する。`if` は下の閉じの規則に従う。
  - 複数行にまたがる計算で `as p ->` をどこに置くかは `fmt-layout` で決める。
- 決定（2026-09-27、`postfix-binding-probe` で試作して測った）: 閉じが要る構文だけを、本体に `->` が無ければ括弧で、あれば `/キーワード` で閉じる。綴りは構文木から 1 通りに決まる。
  - `if` は、本体に `->` があれば `/if` で閉じる。無ければ、後ろに続き（`->`・`as`・`|>`・二項演算子・後ろの引数）があるときだけ括弧で閉じ（`if(fetch true | Yes => 1 | 0) as scrutinee ->`）、続きが無ければ閉じない（`if c => a | b`）。
  - `if` の直後の `(` は、対応する `)` までの最上位に `=>` があるときだけ閉じの開きと読み、無ければ条件の括弧と読む。空白には依らない。`fn(...)` と `fn … /fn` の中の `=>` は最上位に数えない。これで条件が `(` で始まる `if` も、裸・`/if`・`if(...)` のどの形でも書ける（`if (a + b) * 2 > c => 1 | c as d -> d + 1 /if`）。
  - `,`・`;`・`)`・`]`・`}` は中の構文も閉じる。リストの要素・レコードの値・引数に置いた `if` は、続きが無ければ印を持たない（`[if a == b => 1 | 0, 2]`、`fn(selected, line => if … | selected)`）。
  - `fn` は引数に置くので常に閉じる。本体に `->` が無ければ今の `fn(x => x + 1)` のまま、あれば `fn x => … /fn` と書く。引数が複数なら括弧を外しただけの `fn a, b => … /fn`（型注釈は `fn x: Int, y: Int => … /fn`）。
  - `def` は閉じない（§12 のとおり次の項目で終わりが決まる）。`module` と `implement` は `/module`・`/implement` で閉じる。
  - 足りない閉じ・余分な閉じ（続きの無い `if(...)` を含む）・形の食い違いは正準形の違反になり、`fmt` が直せる。閉じ違い（`if … /fn`）は E100 としてその場で報告する。
  - `/` の直後に `if` を置く形は今 E100 なので、`/if` は空白の有無によらず除算と衝突しない。`/fn` は `/fn` で閉じる `fn` の中だけ閉じと読む。`fn` を二項演算子の被演算子に直接置く形（`10 / fn(x => x)`、今は E305）は E100 にする。§6 の `/` に閉じの読みが加わる。
  - 試作では、受理コーパス・拒否コーパス・stdlib・`tools` の 196 ファイルが同じ構文木へ往復し、受理 111 件の実行が一致した。`NodeKind` に変種は要らず、単相化以降は変わらない。拒否コーパスのうち E404・E516・E517 の 3 本は、構文木が綴りを持たないので変換すると欠陥が消える。本実装では手で書き換える。
  - 本体に `->` を 1 つ足すと形が変わる（`fn(x => x + 1)` が `fn x => … /fn` になる）。1 行でも `->` があれば `/if` が付く。
- 退ける: `do` を前置のまま残す（計算より先に扱いを決めさせる点で、前置の `let` と同じ問題を持つ）。値を捨てる行を `e as _ ->` と書く（名前を付けないことをわざわざ書く）。すべての行を `do` で始めて `do e as p ->` とする（純粋な計算に `do` が付き、`do` の意図と食い違う）。`if` の範囲を字下げで決める（空白に意味を持たせない原則を覆す）。閉じる印の綴りのうち、`end`（何の終わりか分からず、`String.slice` の引数名と衝突する）、`endif`（長い）、`.if`（フィールド参照に衝突する）。`if` の閉じを常に括弧にする（末尾の `if` にも 2 文字が付き、長い本体で `)` が何を閉じるか読みにくい）。`fi` の類の閉じる印（1 行では `Write fi` が適用に見える）。空の腕で合流を示す `| ->`（1 行では fallback の腕に見える）。`->` を常に最後の腕に付け、`if` 全体へは `(if …) ->` と囲む形と、最後の腕の後ろの `->` を `if` 全体に付ける形（どちらも閉じの印を持たず、腕の対称と見た目のどちらかを崩す）。`if` の直後の `(` を常に閉じと読む形（本体に `->` を持ち条件が `(` で始まる `if` に綴りが無くなる）。区切りの前の `if` にも `if(...)` を要る形（同じ構文木に 2 通りの綴りが残る）。
- 追随するもの: 仕様の §11・§34・§35・§40・§53 と E101 の「継続」の定義、E501・E504・E505・E506 の文言と書き換え、正規形の印字と `fmt`、tree-sitter の文法。閉じる印のための §6・§12・§23〜§26.1・§30 と、受理コーパス・stdlib・`tools` の閉じが要る構文。`crates/hado/src/mono.rs` の `make_continuation` は構文木しか見ないので変わらない（試作で `NodeKind` に変種が要らなかった）。
- Option に裸の `e ->` は、今の `do` と同じく None を伝播する。本体の戻り型が Option でなければ E305 になる（`postfix-binding-probe` の N9。旧構文の `def main = do find 1 -> 2` も E305）。

## 完了条件

- 選んだ構文と `if` の後ろの規則が仕様に書かれ、旧形（`let` と `do`）が E100 になる。
- `if` 全体に続ける形と、最後の腕に続ける形の両方を受理コーパスが固定し、実行結果が規則どおりになる。
- 閉じの不足・余分・食い違いと、条件が `(` で始まる `if` の 3 つの形を、受理・拒否のコーパスが固定する。
- `cargo test --offline` が 0 failed、`bash scripts/lint-docs.sh` が PASSED。

## 由来

2026-09-26 の相談。先例は SQL の `SELECT … AS name`、Clojure の `as->`、Haskell の `where`。§11、§34、§35、§36、§53、E101、E303。関連する issue は `do-option-absent` と `fmt-layout`。
