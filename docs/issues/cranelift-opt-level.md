# Cranelift の `opt_level` を測る（cranelift-opt-level）
優先度: 低。

## 現象

`crates/hado/src/emit.rs:23` で `opt_level` は `"none"` である。いまの遅さの主因ではない（2026-09-17）。`"speed"` にしたときの差は未計測。

```
$ grep -n 'opt_level' crates/hado/src/emit.rs
23:        .set("opt_level", "none")
```

| ループ | 反復 | 時間 |
| --- | --- | --- |
| 文字列比較 | 1000 万 | 0.08 s |
| 末尾再帰 | 1000 万 | 0.14 s |

## 原因

`crates/hado/src/emit.rs` の `make_isa` が Cranelift の `opt_level` を `"none"` に固定している。`"speed"` との差を測った記録が無く、既定を選ぶ根拠が無いまま残っている。

## 案

- 現象の文字列比較（`==` 10000000 回）と末尾再帰（10000000 回）と `string-split-linear` の入力で `"speed"` と比べ、差が 2 倍未満なら閉じる。観測は判定器がソースと入力から独立に計算した期待値と先に照合する。
- 上げるなら `build` の既定にし、`check` は触らない。

## 完了条件

- 計測の表がラウンドファイルにある。2 つのループは現象の文字列比較（`==` を 10000000 回）と末尾再帰（10000000 回）である。そのソースと、入力（`string-split-linear` の入力も）を生成する手順をラウンドの成果物としてリポジトリに入れる。`string-split-linear` の入力は、その issue の完了条件と同じ生成手順で、小さい側の中央値が 200 ms 以上になる大きさの入力を再生成してバイト一致させる。門番は入れたソースをそのまま使う。トラッキングされたソースを使わずに再構成したループで測る門番、10000000 回に満たない反復、`==` でも末尾再帰でもない別の計算に差し替えたソース、別の短い入力では通らない。同じ 2 つのループと入力それぞれで `"none"` と `"speed"` を warm-up 後 5 回測り、各入力の比（`"none"` の中央値 ÷ `"speed"` の中央値）を出す。3 つの比の中央値を判定値とするが、中央値だけで既定を決めない。各入力（トラッキングされた 3 本）に個別の下限を置き、1 本でも 1.1 倍を下回る（`"none"` ÷ `"speed"` が 1.1 未満。`"speed"` が 1.1 倍の改善に届かない）入力があれば、中央値が 2 倍以上でも既定を `"none"` のままにする。逆に 1 本でも 2 倍以上の入力があっても、他の入力が下限を割れば `"speed"` にしない。判定は「3 本すべてが 1.1 倍以上、かつ中央値が 2 倍以上」のときだけ `"speed"` とし、それ以外は `"none"` とする（比 `3.0`・`3.0`・`0.1` は `"none"`、`10.0`・`1.1`・`1.1` も `"none"`）。各判定値と各入力の比をラウンドファイルの表に書き、どの入力が下限を決めたかを書く。中央値だけを判定に使う門番、下限を判定値の表に書かない門番では通らない。各プログラムの観測結果が両方の最適化水準で同じであることを先に照合する。期待値はいずれかの最適化水準の出力から採らず、判定器がコンパイラを走らせずに計算する。文字列比較はソースの被演算子を独立に `==` して得る真偽、末尾再帰はソースの基底と反復 10000000 から独立に計算した値、`string-split-linear` の入力を読む側は再生成した入力から独立に計算した値と照合する。両水準の一致だけを見る、片方の水準の出力を期待値にする実装では通らない。ループの構造・観測結果・入力を計測の間で変える実装では通らない。
- 判定値が 2 倍未満、または 3 本のうち 1 本でも 1.1 倍未満なら `crates/hado/src/emit.rs:23` は `"none"` のままとし、`build` と `hado run` の既定を変えない。`"speed"` にしない条件の補集合がこの枝である。
- 「3 本すべてが 1.1 倍以上、かつ中央値が 2 倍以上」のときだけ `build` の既定を `"speed"` にし、生成した実行ファイルの実行時間で同じ判定値を再現する。`hado run` の既定はこの条件に加えて、起動・コンパイル・リンク込みの end-to-end の表でも 3 本すべてが `"none"` の 1.1 倍以上であることを要求する。`execute` は呼び出しごとにコンパイルとリンクをするので、子プロセスの実行時間だけでは `run` の使い勝手を決められない。end-to-end で 1 本でも 1.1 倍未満なら `build` だけを `"speed"` にし、`run` は `"none"` のままにする（`run` の end-to-end の表を判定に使わない実装では通らない）。`hado run` は `crates/hado/src/main.rs:266` の `execute` が読み込み・コンパイル・リンクをしてから子を走らせるので、`hado run` の計測は 2 つの表に分ける。子プロセスの実行時間の表は `build` の判定値の再現にだけ使い、起動・コンパイル・リンク込みの end-to-end の表が `run` の既定を決める（end-to-end を記録するだけで判定に使わない実装では通らない）。`check` は emit を通らないので、`check` の診断と `--print-type` が変わらないことを対照に置く。

## 由来

`docs/wants.md` に無い。
