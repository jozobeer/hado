# R49 効果行付き関数値の build 失敗を直す手順書（2026-09-16）（r49）
旧 `docs/plan.md` 45 節。実測は `docs/ledger.md`。

## 手順書

### 背景

`docs/bug.md` の「効果行付きの関数値を返す member の build が失敗する」を直す。`check` は通り、`build` と `run` は `specialization failed: Mismatch` で落ちる。実用の穴である（`docs/rounds/r48.md`の `run` は通るのに、効果行付きの関数値を渡すと落ちる）。

### 実測した原因

- 単相化の `Type` は効果行を持たない。`Ty::Fn(args, result, _) → Type::Closure(args, result)` で行を落とす（`crates/hado/src/mono.rs`）。逆に `Type::Closure` を `Ty` に戻す `From<&Type> for Ty` は `Ty::fn_of` を使い、行を `Row::pure()` にしていた。
- `Signature::specialize_result` と呼び出し先を特殊化する `specialize_function` は、呼び出し側の `Type` から作った `Ty` を**定義の scheme と単一化**する。scheme が `Fn(String => String {Error})` と言い、`Type` 由来の `Ty` が pure と言うので `Mismatch` になる。
- 最小再現は次である（`check` は 0、`build` は 1）。

```ocaml
def apply f x => f x
def make(s: String): Fn(String => String {Error}) Pure => fn(t => String.concat s (Int.to_string (Int.parse t)))
def main = apply (make "x") "7"
```

- ラムダ式を直接渡す形（`apply (fn(t => ...)) "7"`）は落ちない。型が推論の中で閉じるので `Type` へ往復しない。`def` の宣言型や `def` が返す関数値を経由したときだけ落ちる。

### 決定

- **決定 1: `Type` から `Ty` へ戻すとき、閉包の行は `Row::pure()` ではなく新しい行変数にする。** `ty_with_fresh_rows` を足し、行を決めるのは定義の scheme であって、行を持たない `Type` ではないようにする。単一化は scheme の `Closed([Error])` を新しい行変数へ結び、`pure` を押し付けない。
- **決定 2: 新しい行変数を使うのは scheme と単一化する場所に限る。** `Signature::specialize_result`、`specialize_function` の concrete、`constructor_fields`、record の field 取得の 4 箇所。`construct` は `Ty` をそのまま `Type` に戻すだけなので `Ty::from` のままにする。
- **決定 3: 仕様は変えない。** 効果は型に現れるという §20 の規則は既にあり、単相化がそれに追いついていなかった。仕様への疑義ではなく実装の不具合である。
- **決定 4: `docs/bug.md` から該当節を消す。** 同文書の「直したら節を消し、経緯は git 履歴に残す」に従う。節と再現の 1 対 1 は `verify-r38.sh` が測るので、節を消しても数は合う。
- **決定 5: 回帰は `crates/hado/tests/build_cli.rs` と `scripts/verify-r49.sh` に置く。** 受理コーパス（`tests/accept`）は仕様の適合を測る場所なので、実装の不具合の再発は CLI の判定に置く。
- **決定 6: 判定器は `scripts/verify-r49.sh` を新設し、層別の full に `r49` を足す。** 46〜48 の門番は動かさない。

### 仕様への疑義（R49 では決めない）

- 効果行を持つ関数値が**パラメータ型の中**に現れる場合（`Fn(Fn(A => B {Error}) => C)`）の単相化は R49 の判定に入れない。同じ経路で直るはずだが、動く program が出てから足す。
- `Type` が行を持たない設計そのものは残す。行を持つ `Type` にするかは、効果が codegen に効くようになるときに決める。

### 期待値の根拠

| 形 | 期待 | 根拠 |
|---|---|---|
| `apply (make "x") "7"`（`make` が `Fn(String => String {Error})` を返す） | `build` が通り、`x7` を印字 | 決定 1、§20 |
| `apply (fn(t => ...)) "7"` | 従来どおり `build` が通り実行できる | 決定 1、49-c |
| `Fn(String => String)` を返す `def` を渡す | 従来どおり | 決定 1、49-c |
| `Option(Fn(String => String {Error}))` の payload | 従来どおり | 決定 2、49-c |
| `docs/bug.md` | 該当節が無い | 決定 4、49-b |

### 成果物

`docs/plan.md`（本節）、`docs/bug.md`、`docs/ledger.md`、`crates/hado/src/mono.rs`、`crates/hado/tests/build_cli.rs`、`scripts/verify-r49.sh`（新設）、`scripts/lib/gate-tiers.sh`。

### 工程

- 工程 0: 計画（本節）と再現の実測。
- 工程 1: `mono.rs` の `ty_with_fresh_rows` と 4 箇所の差し替え。`build_cli` に回帰テストを足す。この時点で既存の `cargo test` が緑。
- 工程 2: `scripts/verify-r49.sh` を新設し、判定 49-a〜49-d を測る。
- 工程 3: `docs/bug.md` の節を消し、層別の full に `r49`、`docs/ledger.md` に R49。全走。

### 判定

`scripts/verify-r49.sh` を新設し、46〜48 の門番はそのまま回す。**入力は生成し、期待値は判定器側で計算する。** control を先に回す。

- 判定 49-a: 効果行付きの関数値を返す `def` を多相関数へ渡す形を生成し（前置と後置の文字列、`Int.parse` の有無、`let` 経由と直接を混ぜて 6 本）、`check` が緑、`build` が緑、実行の出力が判定器の計算と一致する。
- 判定 49-b: `docs/bug.md` に該当節が無く、`build_cli` の回帰テストが緑。
- 判定 49-c: 効果行の無い関数値と、効果行付き関数値をフィールドに持つ record が従来どおり build できて実行できる。
- 判定 49-d: 層別の full に `r49` があり、corpus lock が緑。

### 許容される赤

工程 1 の途中は `build_cli` が赤でよい。工程 2 の直後に 49-a〜49-d が緑、工程 3 で全走が緑になる。**R49 の終了時に許容される赤は無い。**

### スコープ外

- `Type` に効果行を持たせる設計変更
- `again` 下の SIGSEGV（`wants.md` の 17）
- 効果行を省いた再帰生成器の E306（`docs/bug.md` の 3 件目）
- 未使用の効果に E513 が出ない件（`docs/bug.md` の 1 件目）

### 確認して報告（決定から）

- `ty_with_fresh_rows` が scheme の閉じた行を上書きしないこと（決定 1）
- 効果の無い関数値の build が変わらないこと（決定 2、49-c）
- `docs/bug.md` の節を消しても `verify-r38.sh` の節と再現の数が合うこと（決定 4）

### 中断の条件

**`ty_with_fresh_rows` が、効果行を実際に検めるべき診断（効果の合わない関数値の受け渡し）を緑にしてしまうなら、止めて報告せよ。**

**効果行を持たない関数値の build が新たに落ちるなら、止めて報告せよ。**
