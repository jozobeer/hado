# R45 複数の scrutinee とパターンの腕の条件列の手順書（2026-09-16）（r45）
旧 `docs/plan.md` 41 節。実測は `docs/ledger.md`。

## 手順書

### 背景

パターン分岐は scrutinee を 1 つしか取れず（§26）、腕の中に分岐を置けない（§30）。2 つの値の構造で分岐し、さらに先頭同士を比較する関数は、判断ごとに定義を割ることになる。`stdlib/list.hd` の `merge` は `merge` `merge_right` `merge_heads` の 3 定義に分かれ、`merge_heads` は位置引数を 7 つ運ぶ。`merge_right` は分岐の続きを運ぶためだけの定義である。

足す形は 2 つで、どちらも既存の構文の延長である。

- **`if` の scrutinee をカンマで並べる。** `if left, right | [], _ => right | _, [] => left | [a, ...rest_a], [b, ...rest_b] => ...`。仕様は `Fn(Int, Int => Int)` の `Int, Int` を「引数列であり tuple ではない」と定めている（§20）。scrutinee の列と腕の pattern の列も同じ読みで、tuple の値は生まれない（E105 と §4 は動かない）。
- **パターンの腕の本体に条件列を置く。** `| [a, ...rest_a], [b, ...rest_b] => if | comparator a b <= 0 => ... | ...`。`=>` の後の `if |` だけを許し、Boolean 二分岐とパターン分岐は腕の中で今まで通り E101 である。条件列は fallback が必須（E401）なので、条件列を持つ腕は構造上必ず値を返し、網羅性はパターンの列だけで決まる。OCaml の `when` のようにパターンを 2 回書くことも、網羅性から外す例外も要らない。

`=>` を省いて `| pattern | condition => ...` と書く形は取らない。fallback（`| default`）も `=>` を持たず、`None` `[]` `x` はパターンとしても式としても読めるので、`| None | x => ...` が「fallback の後の腕（E404）」なのか「`None` の腕の条件列」なのか構文で決まらない。`=> if |` は既存の「`if` の直後が `|` なら条件列」（付録C）をそのまま腕の本体に許す形で、曖昧さが無い。

merge は 1 定義になる。

```
def rec merge left right comparator =>
  if left, right
  | [], _ => right
  | _, [] => left
  | [a, ...rest_a], [b, ...rest_b] => if
    | comparator a b <= 0 => [a, ...merge rest_a right comparator]
    | [b, ...merge left rest_b comparator]
```

### 決定

- **決定 1: `if` は scrutinee を 1 つ以上取り、腕の pattern は scrutinee と同じ数を並べる。** 数が合わない腕は E125（`pattern-column-count`、構文、アンカーはその腕の `|`）。fallback は式 1 つで、列の数に関わらず 1 つである。§23、§26、§56、付録C を改める。第31節の形（`def f | ...`、`fn(| ...)`）は arity 1 のままで、列を増やす形は R45 の範囲外（`docs/wants.md` に送る）。
- **決定 2: パターンの腕の本体は `arm_body` か条件列（`if` `|` ...）である。** 腕の条件列は fallback で終わり、fallback の後の `|` は外側の次の腕である。fallback を持たない腕の条件列は、続く `|` の腕を自分の条件として読む（§32 が `Some(y)` を式として読むのと同じ扱いで、仕様に一文で書く）。条件列の腕の中の分岐、腕の中の Boolean 二分岐とパターン分岐、`let` の継続と `fn` の本体の分岐は E101 のままである。§30 の原則は `branch depth <= 1` から「腕の本体に置ける分岐は条件列だけで、条件列の腕には分岐を置けない」に言い換える。§30 と付録C を改める。
- **決定 3: 列の規則。** E512（最上位の変数パターン）と E503（catch-all の `_`）は、行の全列が変数か `_` のときだけ当てる（E512 は変数を 1 つでも含む行、E503 は全列 `_` の行）。列の一部が `_` の行（`| _, [] => left`）は受理である。Bool リテラルの列は列が 2 つ以上なら受理し（Boolean 二分岐に書き換えられないため）、列が 1 つのときは §24 のままである。非 Bool リテラルはどの列にあっても fallback 必須（E402）。E507 と E508 は scrutinee が 1 つのときだけ当てる。E515 は scrutinee が 1 つで引数が 1 つのときだけ当てる（既存のまま）。§24、§26、§29 を改める。
- **決定 4: 腕の条件列の規則。** E401（fallback 必須）、E406、E511 は腕の条件列にもそのまま当てる。fallback の後の `|` は外側の腕なので、腕の条件列の中で E404 は起きない。E401 と E511 のアンカーは腕の `if`。E520 は腕の条件列に当てない（`| p => if | c => a | b` は `| p => if c => a | b` が E101 なので正準形。§32 の `def f x | c => a | b` と同じ理由）。条件列を持つ腕は E402、E403、E405 の判定で「その pattern の行を全域で覆う」腕として数える（fallback 必須の帰結）。§24、§56 を改める。
- **決定 5: 網羅性は行列で判定する。** `crates/hado/src/coverage.rs` の `covers` は既に行（`Vec<Cell>`）の列を左から特殊化する形なので、1 行に列の数だけ cell を並べて渡す。E402 は `Some(false)`、E403 は fallback 付きの `Some(true)`、`None`（リテラル等で決まらない）は今まで通り報告しない。
- **決定 6: 単相化は列を左から特殊化した `Switch` の入れ子で下ろす。** `constructor_switch` を列ごとに適用し、`_` と変数の行は各 constructor の特殊化に持ち込む。行の順序（先勝ち）を各特殊化で保つ。failure 継続を行数 × 列数で複製しない（複製されるのは `_` の行の本体だけで、上限は constructor 数の列数乗）。リテラルの列は既存の等値テストの連鎖、record の列は束縛のみである。
- **決定 7: AST は `PatternBranch { scrutinees: Vec<Node>, arms: Vec<(Vec<Pattern>, Node)>, fallback }` にする。** scrutinee 1 つは長さ 1 の列である。腕の条件列は本体の `Node` が `CondBranch` である形で表し、新しい `NodeKind` は足さない。正規形印字（`canonical`、`source_print`）は `if a, b | p, q => ...` と `=> if | ...` を印字し、往復（parse → print → parse）で同じ木になる。
- **決定 8: 生成文法を追随させる。** `crates/hado/tests/r9_grammar.rs` の生成器は付録C の規則名と選択肢を全て訪れることを自分で確かめるので、付録C に足した規則（scrutinee の列、pattern の列、腕の条件列）を生成器も生成する。
- **決定 9: `stdlib/list.hd` の `merge` を 1 定義にし、`merge_right` `merge_heads` を消す。** 契約 `module List` に `merge` は無いので契約は変えない。`List.sort` を使う受理コーパスが無い（実測 0 本）ので、`tests/accept/list_sort/` を足して stdlib の書き換えを実行で測る。
- **決定 10: コーパスと判定器。** 受理に `columns_merge`（複数 scrutinee と腕の条件列、§26）、`arm_conditions`（第31節の形の腕の条件列、§26.1）、`list_sort`（§55、`needs: prelude`）、拒否に `E125` を足す。`scripts/verify-r45.sh` を新設し、`scripts/lib/gate-tiers.sh` の full に `r45` を足す。lock はコーパスと stdlib の工程でだけ作り直す。
- **決定 11: 版（`v0.3.1`）と tag は R45 では動かさない。** 言語意味が増えるので、tag を打つ時点で版を上げるかを決める。`docs/wants.md` の「次は診断と fmt（言語意味を増やさない）」は、R45 が先に言語意味を 1 つ足した事実に合わせて直す。
- **決定 12: 実装は cursor（`cursor-grok-4.6-xhigh`）へ工程ごとに委譲する。** 作業ツリーは `.worktrees/r45`（branch `r45-pattern-columns`）、ビルド先は `CARGO_TARGET_DIR=<worktree>/.target`。判定器とコーパスを先に書いて赤を実測してから委譲し、依頼書は判定器の項目を指す。builder は `docs/` `tests/accept` `tests/reject` `stdlib/` `tests/corpus.sha256` を触らず、コミットしない。門番の全走と `cargo test` の全走は指揮者が回す。

### 仕様への疑義（R45 では決めない）

- **入れ子パターンの同名束縛。** `Pair(x, x)` は今も受理される（実測、2026-09-16）。列をまたぐ同名束縛（`| x, x =>`）も同じ扱いになる。禁止するかは §26 に規則が無いので R46 以降に送る。
- **fallback を持たない腕の条件列が続く腕を飲む形の診断。** 決定 2 は §32 と同じく「式として読む」側を選ぶ。専用の診断を出すかは頻発してから決める。

### 期待値の根拠

| 形 | 期待 | 根拠 |
|---|---|---|
| `if a, b \| [], _ => x \| _, [] => y \| [_, ..._], [_, ..._] => z` | 受理 | 決定 1、決定 3 |
| `if a, b \| [] => x \| ...` | E125、腕の `\|` | 決定 1 |
| `if a, b \| x, y => ...` | E512 | 決定 3 |
| `if a, b \| _, _ => x \| y` | E503 | 決定 3 |
| `if a, b \| true, false => x \| ...` | 受理 | 決定 3 |
| `if a \| true => x \| false => y` | E520 | §24（変えない） |
| `\| p => if \| c => a \| b` | 受理 | 決定 2 |
| `\| p => if \| c => a` に続く腕が無い | E401、腕の `if` | 決定 4 |
| `\| p => if \| c => a \| b` の 1 本の条件 | E520 にならない | 決定 4 |
| `\| p => if c => a \| b`、`\| p => if x \| ...`、`\| c => if \| ...` | E101 | 決定 2 |

### 判定

`scripts/verify-r45.sh` を新設する。構造は `scripts/verify-r43.sh` に倣う。**入力の形が列挙できる判定は分類から生成する。期待値は判定器側で計算し、コーパスのファイル名や行を埋め込まない。** 比較が差を検出できることを control で先に確かめる。

- 判定 45-a: 網羅性の行列。小さな ADT（constructor 2〜3 個、payload 0〜1 個）を 2〜3 列に並べ、`_` を混ぜた行を乱数で作る。判定器が同じ行列アルゴリズムで網羅性を計算し、fallback 無しの非網羅は E402、fallback 付きの網羅は E403、それ以外は受理であることを `hado check` と照合する。網羅と非網羅の両方が現れたことを数える。
- 判定 45-b: 腕の条件列。(1) merge の形が check を通り、乱数の 2 列の昇順リストの merge が判定器の計算と一致する。(2) fallback の無い腕の条件列が E401 で、アンカーが腕の `if`。(3) 条件が 1 本の腕の条件列が E520 にならない。(4) `=> if c => a | b`、`=> if x | ...`、条件列の腕の中の `if |` が E101。
- 判定 45-c: 列の規則。列の数が少ない腕と多い腕が E125 でアンカーが腕の `|`、全列が変数の行が E512、全列 `_` の行が E503、`| _, [] =>` が受理、2 列の Bool リテラルが受理、1 列の Bool リテラルが E520。
- 判定 45-d: 既存の読みが動かない。`| None | Some(x) => x` が E404、`| default` が最後の形が受理。
- 判定 45-e: 仕様と文法。§30 の言い換えの文が逐語で 1 回ある。付録C に `pattern_branch` の scrutinee の列、`pattern_arm` の pattern の列と条件列の選択肢がある。`cargo test --offline -q --test r9_grammar` が緑。
- 判定 45-f: stdlib。`stdlib/list.hd` に `def rec merge` が 1 つで `merge_right` `merge_heads` が無い。乱数の Int リストを `List.sort` で並べた出力が判定器の計算と一致する。
- 判定 45-g: `cargo test --offline --no-fail-fast` が 0 failed。
- 判定 45-h: gate-tiers の full に `r45` があり、`bash scripts/run-gates.sh --tier full` が exit 0 で `^NG:` が 0。
