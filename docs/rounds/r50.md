# R50 スタックの枯渇を診断にする手順書（2026-09-16）（r50）
旧 `docs/plan.md` 46 節。実測は `docs/ledger.md`。

## 手順書

### 背景

§53 は「`again` を含むループはスタックを反復回数に比例して消費する」と決めている。しかし尽きたときに何が起きるかを決めていないので、いまは SIGSEGV で黙って死ぬ（`wants.md` の 17 と 35）。`check` が通り `build` も通るのに、実行だけがシグナルで消えるのは「check は通るが実行できない」の 2 件目である。R50 は、尽きたときに**言語の診断**（メッセージと終了コード）へ閉じる。

### 実測した現状

`tests/accept/again_loop/main.hd` の形（`again` の handler が `resume` を呼び、`def rec loop` が `do yield` を繰り返す）で反復回数を変えて測った。`ulimit -s` は 8192 KB。

| 反復 | 結果 |
|---|---|
| 100,000 | 完走（`100000` を印字、終了 0） |
| 200,000 | 完走 |
| 400,000 | SIGSEGV（終了 139、メッセージ無し） |
| 1,000,000 | SIGSEGV（終了 139、メッセージ無し） |

したがって 1 反復あたり約 20〜40 バイトを消費している。`docs/plan.md` 17.8 の「約 3 万反復」は Koka 3.2.3 の実測であり、Hado の現在の実装はもっと遅く尽きる。**上限の数値を仕様に書かない**（実装の定数になるため）。仕様に書くのは「尽きたときの観測される振る舞い」だけにする。

### 決定

- **決定 1: スタックの枯渇を SIGSEGV ではなく診断にする。** 尽きたら stderr に `hado: stack overflow` の 1 行を出し、終了コード 1 で終わる。終了コード 1 は `raise` と `hado: print failed` と同じ「実行時の失敗」である。
- **決定 2: 判定はシグナルのハンドラで行い、スタックの底の近くで起きたフォールトだけを枯渇とみなす。** `getrlimit(RLIMIT_STACK)` と `main` の局所変数のアドレスから底を概算し、フォールトしたアドレスが底の前後 1 MB に入るときだけ枯渇とする。ヌル参照（アドレス 0）や底から遠いフォールトは枯渇ではない。
- **決定 3: 枯渇でないフォールトは握り潰さない。** 先に設置されていたハンドラ（Boehm GC など）へそのまま渡し、無ければ既定の動作に戻して raise し直す。診断を足すことで本物の不具合が見えなくなるのを避ける。
- **決定 4: ハンドラは代替シグナルスタックで走らせる。** 枯渇した状態では通常のスタックにハンドラを積めないので `sigaltstack` を使う。
- **決定 5: ハンドラは起動時に 1 回だけ設置し、`hado_entry` の後には何もしない。** 通常の実行の費用は `getrlimit` と `sigaltstack` と `sigaction` の数回だけで、ループの中には何も足さない。
- **決定 6: 仕様は §53 の直後に `§53.1` を足す。** 反復回数の上限は書かず、尽きたときの出力と終了コードだけを書く。
- **決定 7: 言語の `Error` にはしない。** `raise` と同じ経路に載せるにはハンドラと `$Outcome` の巻き戻しが要り、生成コードの呼び出し規約に踏み込む。R50 は診断までとし、`{Error}` にするのは `wants.md` の 35 に残す。
- **決定 8: 判定器は `scripts/verify-r50.sh` を新設し、層別の full に `r50` を足す。** 49 までの門番は動かさない。

### 仕様への疑義（R50 では決めない）

- 枯渇の終了コードを 1 とするか、`raise` と区別する別の値にするか。いまは `raise` と同じ 1 にした。終了コードを分ける実プログラムが出たら決める（`wants.md` の 25）。
- 反復回数の上限を仕様に書くか（`wants.md` の 17）。実装依存の数値なので、R50 では書かない。

### 期待値の根拠

| 形 | 期待 | 根拠 |
|---|---|---|
| 深い `again` ループを 1 MB のスタックで走らせる | stderr が `hado: stack overflow`、終了 1、stdout は空 | 決定 1、決定 2、§53.1 |
| 同じプログラムを 64 MB のスタックで走らせる | 完走して反復回数を印字、終了 0 | 決定 2（枯渇でないときは何もしない） |
| 浅いループを 1 MB で走らせる | 完走、終了 0 | 決定 2 |
| 通常の終了・`raise`・`print failed` | 従来どおり | 決定 3、決定 5 |

### 工程

- 工程 0: 計画（本節）と現状の実測（上の表）。
- 工程 1: 仕様 `§53.1` と追跡表 1 行と `wants.md` の更新。
- 工程 2: `scripts/verify-r50.sh` を新設し、層別の full に足す。この時点で 50-a は赤（SIGSEGV）。
- 工程 3: `runtime/hado_runtime.c` にハンドラを足し、判定 50-a〜50-d を緑にする。
- 工程 4: 全走と台帳。

### 判定

`scripts/verify-r50.sh` を新設し、49 までの門番はそのまま回す。**入力は生成し、期待値は判定器側で計算する。** control を先に回す。

- 判定 50-a: `again` の深いループ（反復 300,000、生成）を `ulimit -s 1024`（1 MB）で走らせ、終了コード 1、stderr が `hado: stack overflow`、stdout が空。
- 判定 50-b: 同じ実行ファイルを `ulimit -s 65536`（64 MB）で走らせ、完走して `300000` を印字、終了 0。枯渇でないときにハンドラが誤発火しないこと。
- 判定 50-c: 反復 1,000 を 1 MB で走らせ、完走して `1000` を印字、終了 0。
- 判定 50-d: `§53.1` が仕様と追跡表にあり、full の層に `r50` があり、corpus lock が緑。

control は、期待値を 1 つずらす（終了コード、メッセージ、印字）と判定が落ちることを確かめる。

### 許容される赤

工程 2 の直後は 50-a が赤（SIGSEGV、終了 139）。工程 3 で緑にする。**R50 の終了時に許容される赤は無い。**

### スコープ外

- 枯渇を言語の `{Error}` として `handler` で捕まえられるようにする（`wants.md` の 35）
- segmented stacks（`wants.md` の 17）
- コンパイラ自身（Rust プロセス）のスタック溢れ。巨大なリテラルの `build` が落ちる件（R34 で実測）は別
- `again` 以外の非末尾再帰の上限を仕様に書くこと

### 確認して報告（決定から）

- 枯渇でないフォールトを握り潰していないこと（決定 3）
- 通常の実行と `raise` の終了コードが変わらないこと（決定 1、決定 5）
- 枯渇していない深いループが従来どおり完走すること（決定 2、50-b）

### 中断の条件

**枯渇でない SIGSEGV が `hado: stack overflow` と表示されるようになるなら、止めて報告せよ。**

**通常の終了コード、`raise` の終了コード、印字のいずれかが変わるなら、止めて報告せよ。**
