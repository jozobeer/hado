# R60 E305 の役割と関連位置の手順書（2026-09-16）（r60）
旧 `docs/plan.md` 56 節。実測は `docs/ledger.md`。

## 手順書

### 背景

`docs/wants.md` の 3「E305 に期待型と実型を載せる」（高）。R56 で適用の引数に `expected <仮引数の型>, found <実引数の型>` を入れ（§15.1）、R58 で関連位置の書式を入れた（§56、`docs/rounds/r58.md`）。残りは「引数以外の食い違いの役割の明示」と「関連位置」である。

§15.1 は第 1 形（`expected …, found …`）を適用の引数だけに許し、それ以外は `cannot unify <a> with <b>` として「2 つの型の順序は箇所によって揃っていないので、対称な言い方にする」と書いている。E305 は日々いちばん出るコードで（§56 の表、アンカーは型が食い違った式の先頭）、いまの文面はどちらが期待でどちらが実際かを書かない。正準形の拒否を直す体験を濁している。

### 実測した材料

リポジトリルートで、その場で書いたプログラムを `cargo run --offline -q -- check` に渡した。

| 書いた形 | いまの出力 |
|---|---|
| `def f (x: Int): Int => "a"`（本体と宣言された戻り型） | `main.hd:1:1: error[E305]: cannot unify String with Int`（アンカーは `def` の先頭） |
| `def f (x: Int): Int => if true => 1 \| "a"`（条件式の腕） | `main.hd:1:39: error[E305]: cannot unify String with Int`（アンカーは後の腕） |
| `def f (x: Int): Int => if x => 1 \| 2`（条件式の条件） | `main.hd:1:27: error[E305]: cannot unify Int with Bool`（アンカーは条件） |
| `type T = { a: Int; b: String }` と `{ a = "x"; b = "y" }`（レコードのフィールド） | `main.hd:2:28: error[E305]: cannot unify String with Int`（アンカーはフィールドの値） |
| `def f (x: Int): Int => x` と `f "a"`（適用の引数。R56） | `main.hd:2:14: error[E305]: expected Int, found String`（アンカーは実引数） |
| `def f (x: Int): Bool => true && x`（論理の被演算子） | `main.hd:1:25: error[E305]: cannot unify Bool with Int`（アンカーは式の先頭 `true`。食い違うのは右の `x`） |
| `def f (x: String): Int => 1 + x`（算術の被演算子） | `main.hd:1:27: error[E305]: cannot unify Int with String`（アンカーは式の先頭 `1`。食い違うのは右の `x`） |
| `def f (x: Int): Int => x == "a"`（比較の被演算子） | `main.hd:1:25: error[E305]: cannot unify Int with String` |
| 対照（食い違いの無い上の形） | 無診断、終了 0 |

順序も揃っていない。`x + "a"` と `x == "a"` は `Int` が先、`true && x` は `Bool` が先である。

今回の射程から外したもの（実測のうえで）。

- 演算子の被演算子（算術と論理）: §56 のアンカーは「型が食い違った式の先頭」で、演算子では式全体の先頭になる。`true && x` のように**食い違っていない側**を指すことがあるので、`expected Bool, found Int` の形にすると、その位置が `Int` であるかのように読めてしまう。対称な文面のままにする。
- 比較の被演算子: 左右のどちらも宣言された期待ではなく、両側が同じ型であることだけが要求される。
- リストの要素と `if` のパターン腕: `def f (x: Int): Int List => [1, "a"]` は `main.hd:1:33: error[E305]: cannot unify String with A`、`type O = | Mine(Int) | Nothing` の腕は `main.hd:2:55: error[E305]: cannot unify String with A` になる。期待の側がまだ解けていない型変数として印字されるので、役割を名指しできない。
- `let` の注釈: `let x: Int = …` も `("a": Int)` も構文が無い（どちらも E100）。式の型を書く構文が無いので、この箇所は存在しない。

### 決定

1. §15.1 の第 1 形を、役割が確定し、かつアンカーが食い違った側を指す箇所へ広げる。stage 1 は (a) 値の定義の本体と宣言された戻り型、(b) 条件式の腕どうし、(c) 条件式の条件（`Bool`）、(d) レコード literal のフィールド、(e) 適用の引数（R56 のまま）。
2. 期待の側が式である箇所には §56 の関連位置を足す。(a) は宣言された戻り型の先頭に、(b) は先の腕の先頭に置く。ラベルは E305 で 1 つ、`expected here` とする（§56 は「ラベルはコードごとに 1 つ」としている）。
3. 条件式の条件とレコードのフィールドには関連位置を足さない。期待の側がアンカーのある式そのもの（条件なら `Bool`、フィールドなら宣言された型）で、隣接する 2 つ目の位置は情報を増やさない。
4. アンカーは §56 の表のまま動かさない。(a) は定義の先頭（`def` の 1 文字目）のままである。
5. 演算子の被演算子、比較の被演算子、リストの要素、期待の側が解けていない型変数になる箇所は第 2 形（`cannot unify <a> with <b>`）のまま。
6. コードを足さない。E305 のままである。書き換えも足さない（役割と位置からは意味を変えずに直せない）。
7. 1 件報告を崩さない。関連位置は行を増やさない（§56）。
8. 型の印字は変えない。§15.1 の改名と行の規則のままである。

### 期待値の根拠

| 箇所 | 期待する文面 | 根拠 |
|---|---|---|
| (a) 宣言された戻り型 | `expected Int, found String`、アンカーは `def` の先頭、関連位置（`expected here`）は戻り型の先頭 | §15.1、§56。材料の 1 行目 |
| (b) 条件式の腕 | `expected Int, found String`、アンカーは後の腕、関連位置は先の腕の先頭 | 同上、材料の 2 行目。先の腕の型が期待になる |
| (c) 条件式の条件 | `expected Bool, found Int`、関連位置なし | 同上、材料の 3 行目。アンカーは条件そのもの |
| (d) レコードのフィールド | `expected Int, found String`、関連位置なし | 同上、材料の 4 行目。アンカーはフィールドの値 |
| (e) 適用の引数 | `expected Int, found String`（R56 のまま） | 同上、材料の 5 行目 |
| (f) 演算子の被演算子 | `cannot unify …`、関連位置なし（アンカーは式の先頭のまま） | 材料の 6・7 行目。アンカーが食い違わない側を指し得る |
| (g) 比較の被演算子 | `cannot unify …`、関連位置なし | 材料の 8 行目。左右対称 |

### 判定

- 60-a (a) 宣言された戻り型: 生成した空行・字下げの下で、文面が `expected Int, found String`、アンカーが定義の先頭、関連位置が戻り型の先頭で `expected here`、行は 1 行、終了 1。
- 60-b (b) 条件式の腕: `expected Int, found String`、アンカーが後の腕の先頭、関連位置が先の腕の先頭。
- 60-c (c) 条件式の条件: `expected Bool, found Int`、関連位置なし。
- 60-d (d) レコードのフィールド: `expected Int, found String`、関連位置なし。
- 60-e (e) 適用の引数: `expected Int, found String`（R56 の形が壊れていない）。
- 60-f 対称な文面の残り: 演算子と比較の被演算子は `cannot unify …` のままで、関連位置を足さない。食い違いの無い対照は受理。
- 60-g 1 件報告: 食い違いを 2 つ持つ形でも 1 行。
- 60-h 書き換えなし: `check --fix` と `fmt` は書かない。
- 60-i 文書と層: §15.1 の一覧、§56 のラベル、追跡表、full 層の r60。
- 60-j corpus lock。

### スコープ外

- 演算子と比較の被演算子、リストの要素、パターンの腕の役割（材料の実測のとおり。アンカーの規則と、解けていない型変数の穴を報告する）。
- 適用の引数の関連位置（呼ばれる側の仮引数の宣言位置。名前の解決が要る）。
- レコードのフィールドの関連位置（型宣言の側の位置。型の名前から宣言を引く仕掛けが要る）。
- アンカーの変更、E305 の書き換え、`--format json`、`explain`、ソース抜粋と caret。
- 効果の型（E601 など）の文面。

### 確認して報告

- 受理コーパスと既存の門番が、文面の変更でどれだけ赤くなったか（コーパスのファイルは変えない）。
- 関連位置のラベル `expected here` が §56 の「コードごとに 1 つ」で足りるか、箇所ごとのラベルにすべきか。
- 期待の側が解けていない型変数のまま印字される箇所（リストの要素、パターンの腕）が他にも無いか。
- 演算子のアンカーが食い違わない側を指すこと（`true && x`）は、§56 の「型が食い違った式の先頭」のままでよいか。

### 中断の条件

- 文面の変更で受理コーパスが赤になり、§15.1 の文だけでは解けないとき。
- 期待の側の位置（戻り型の先頭、先の腕の先頭）が実装から取れないとき。
