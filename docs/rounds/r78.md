# R78: 配布する Hado コードをパイプライン中心にする（2026-09-17）（r78）
旧 `docs/plan.md` 73 節。実測は `docs/ledger.md`。

## 手順書

### 背景
標準ライブラリと、利用者が読む実用サンプルの関数適用はほぼ直接適用のままで、§14 の data-first なパイプラインを日常の書き方として示せていない。

### 決定
- `stdlib/`、`tools/`、付録Bの典型コードと対応する受理ケースを対象にする。`tests/accept/` 全体はサンプル集ではなく構文ごとの判定器なので、付録B以外は対象にしない。
- constructor 呼び出しと、直接適用そのものを検証する受理ケースの式は直接適用のまま残す。`tests/reject/` は 1 ファイル 1 欠陥の入力なので触らない。
- それ以外の直接適用 `f value rest` は `value |> f rest` に寄せる。型、評価順、効果、期待出力は変えない。
- 残る直接適用は構文木から列挙し、ファイル名・位置・式を理由付きの例外として固定する。新しい無理由の直接適用は門番で赤にする。

### 成果物
- 配布対象の `.hd` / `.hdi` と `docs/spec.md` 付録B。
- 残存例外を検査する Rust の統合テスト。
- `tests/corpus.sha256` と `docs/ledger.md`。

### 工程
1. この手順書をコミットする（`docs:`）。
2. 構文木から直接適用を列挙する検査を書き、現状で赤を測る（`test:`）。
3. 1 ファイルずつパイプラインへ移し、対象の `check` または既存テストで確かめる（`refactor:`）。
4. corpus lock を更新し、quick、`cargo test`、台帳を 1 回ずつ走らせて閉じる（`docs:`）。

### 判定
- 78-a 対象に残る直接適用が、直接適用そのものを検証する例外と一致する。
- 78-b `stdlib/` の各ファイルが `hado check` を通る。
- 78-c 受理・ライブラリコーパスの既存の判定が変わらない。
- 78-d `tools/gates/main.hd` と `tools/diagnostics/main.hd` が既存の実行経路で動く。
- 78-e corpus lock、quick、`cargo test` が緑である。

### 中断の条件
- パイプラインへの置換で型、効果、評価順のいずれかが変わるとき。
- 直接適用を残さないと既存の構文被覆が失われるが、例外を一意に固定できないとき。
