# コーパスと門番

`tests/accept/` と `tests/reject/` のコーパスは、M2 以降の全マイルストーンの判定器である。
仕様は `docs/spec.0.1.md`、工程は `docs/plan.0.1.md`、各ラウンドの経緯は `docs/ledger.0.1.md`。

## ヘッダタグ

各ファイルの冒頭に置く。`--` 行コメント（§43）なので、コーパス自身が shin として妥当である。

| タグ | 付ける対象 | 意味 |
|---|---|---|
| `-- spec: §N` | 全件 | 根拠となる仕様の節。`N` は `docs/spec.0.1.md` に実在する見出し番号 |
| `-- error: EXXX` | 拒否のみ | 期待するエラーコード。§50 の表と 1 対 1 |
| `-- expect: <文字列>` | 受理のみ | 実行したときの stdout（trim 後） |
| `-- item: <項目名>` | 任意 | `docs/plan.0.1.md` 2.2 の項目名。`docs/spec-coverage.0.1.md` と文字列一致 |
| `-- needs: prelude` | 受理のみ | prelude の関数を使う。M3〜M6 の判定から除外される |
| `-- short-circuit:` | 受理のみ | 短絡評価の検証用。値は短絡する演算子。評価されない側に停止しない再帰を置く |

## 1 ファイル 1 欠陥

拒否コーパスは、**タグのコードがそのファイルの唯一かつ最初に当たる欠陥**でなければならない。

検査は 字句 → 構文 → 名前解決 → 型 → 網羅性 → 冗長 の順に走る。先に別の禁止に当たると、
タグのコードまで到達せず、そのコーパスはコードを検証できない。

実例（R3 で見つかり、修正した）:

- `E101`（分岐のネスト）を狙ったファイルに `.5` があり、字句で先に落ちていた
- `E501`（identity binding）のファイルが `def f x => x` で、これは §9 が許す identity 関数だった

持ち越しの既知の欠陥:

- **`tests/reject/E508.shin`** は `| Ok(user) => user` と `| Error(error) => Error(error)` で
  両枝の型が違う。`if` は 1 つの型の式なので、**型検査が冗長検査（E508）より先に当たる**。
  M4 の着手時に直す。仕様 §24 の例は成功枝が `...`（Result 側の継続）で、
  コーパスがそこを `user` で埋めたことが原因

## `-- item:` は被覆のために寄せない

`docs/plan.0.1.md:154` は「2.2 の各項目に受理と拒否のペアが 1 組以上」と要求する（**（推定）**印つき）。
判定器はタグの**形式と集合**しか見ないので、数を満たすためにタグを近くのファイルへ貼ると、
その項目の例が嘘になる。R3 では 3 ラウンドかけてこれを潰した。

**拒否側は 20 項目のみを対象とする。** 次の 2 項目は拒否例が原理的に存在しない:

| 項目 | 理由 |
|---|---|
| `冗長の対象外` | eta 展開を「冗長としない」という**許可**の規定。拒否すべき形が定義上存在しない |
| `末尾呼び出し` | 「スタックを消費しない」という**保証**の規定。禁止ではない |

## エラーコードは仕様の禁止から導く

拒否コーパスは §50 の表と 1 対 1 で、**表の行数がコーパスの本数**である（現在 46）。
コードを足したら、コーパスと `scripts/verify-m1-corpus.sh` と
`crates/shin/tests/parse_corpus.rs` の件数を追随させる。

**仕様が禁止していてコードが無い箇所は、コーパスが書けない = 永遠に検証されない。**
実際に 2 度見つかっている:

- R3: 構文の禁止 4 件（リテラルの形・コメントの記法・tuple・呼び出しの形）→ E103〜E106 を追加
- R5: 型と名前解決の頻出エラー 2 件（型の不一致・未束縛の名前）→ E205 / E305 / E306 を追加

コーパスや検査器を書く作業は、仕様のレビューを兼ねている。

## 門番スクリプト

いずれもリポジトリルートから実行し、`OK:` / `NG:` を 1 行ずつ出して最後に `PASSED: n/N` を出す。
1 つでも NG なら終了コードが非 0。

| スクリプト | 守るもの |
|---|---|
| `verify-m0.sh` | ワークスペース・依存・ISA flags・ランタイムの記号・walk と tail のテスト |
| `verify-m1-spec.sh` | §1〜§42 の見出しが無傷、新設節が §43 以降、エラーコード表の形式、35 項目の対応表 |
| `verify-m1-corpus.sh` | 拒否がコード表と 1 対 1、§39 の例の被覆、22 項目の被覆、`corpus.rs` が本当に列挙していること |
| `verify-m2.sh` | 受理 23 が parse、E1xx 7 が指定コードと指定位置で落ちる、非 E1xx 39 が parse、式木の往復 |

### ラウンド固有の保護を焼き込まない

`verify-m1-corpus.sh` のチェック 7 は当初 `crates/shin/src` の変更を禁じていた。これは
「R3 は src を触らない」というラウンド固有の約束を永続スクリプトに焼き込んだもので、
**M2 が src を書いた瞬間に偽陽性**になった。

門番が守るべきは**マイルストーンの完了条件**であって、あるラウンドの作業範囲ではない。

### 件数の直書きを禁じる

`corpus.rs` は `read_dir` で列挙し、件数を出力する。列挙が本物かは、
`tests/accept/` に一時ファイルを置いて **`corpus_enumerated:` が 1 増えるか**で確かめる
（`verify-m1-corpus.sh` のチェック 5）。件数を定数で持つ実装はここで落ちる。

## 暗記で満たせない判定器

入力がリポジトリに固定された判定器は、その入力だけを特別扱いする実装で通せてしまう。
M2 の受け入れ条件を設計する過程で、実装を一切しない結託が 5 段階にわたって判定を
すり抜けた（`docs/ledger.0.1.md` の R4・R5）。**入力を実行時に生成し、期待値は
判定器側で計算する**のが対処で、このリポジトリでは次の形になっている:

| 判定器 | 形 |
|---|---|
| `corpus.rs` の列挙 | 一時ファイルを置いて件数が動くか（`verify-m1-corpus.sh` チェック 5）|
| `parse_corpus.rs` の式木の往復 | 乱数で式木を作り、冗長な括弧・空白・行コメントを混ぜて描画し、完全括弧付きの正規形を照合する |
| 位置情報 | `-- error:` 行の直後に空行を入れると報告行が 1 増える。空白を 2 つ足すと列が 2 増える |

**式木の往復は結合性を見ていない。** 描画側が優先順位から必要な括弧を必ず付けるため、
`a * b * c` のような無括弧の連鎖がソースに現れない。結合性は
`parser::tests::left_assoc_add_and_mul` が固定しており、`verify-m2.sh` が `cargo test` 全体を
見ることで捕まえる。

## 既知の債務

`crates/shin/src/lib.rs` の `lower_to_m0` が余剰のトップレベル `def` を弾かない。
`def other = 1` と `def main = 1 + 2` が並ぶと `compile_to_object` が成功する。
名前解決と未使用 `def` の検査（E513）は M3・M4 の担当。

拒否コーパスの `E508.shin` については「1 ファイル 1 欠陥」の節を見る。
